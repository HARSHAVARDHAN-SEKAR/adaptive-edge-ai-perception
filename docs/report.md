# Adaptive Multi-Modal Edge Perception for Autonomous Mobile Robots
### Research report source notes

**Author:** Harshavardhan Coimbatore Sekar

## 1. Abstract

Mobile robots have limited edge-compute budgets, so running every perception
model on every frame is often impractical. This project implements an adaptive
perception engine that changes perception breadth per frame according to fused
scene risk and live resource telemetry. The scheduler combines an attention
state (PATROL / ALERT / ENGAGED) with a resource state
(NORMAL / CONSTRAINED / CRITICAL), then selects the best feasible model plan.

The scheduler benchmark uses deterministic synthetic scenes and
latency-simulating mock models. It evaluates scheduling behaviour, load
shedding and event coverage; it is **not** a real-model accuracy, power or
Jetson-performance benchmark. The numerical source of truth is
`assets/bench_scheduler.json`, regenerated by
`python -m benchmark.latency_test --frames 120`.

## 2. Architecture

Camera -> Adaptive Scheduler -> Model Plan -> Multi-Model Inference ->
Perception Fusion -> ROS 2 outputs.

The perception tiers are:

| Task | Implementation | Role |
|---|---|---|
| Detection | Ultralytics YOLOv8 n/s/l | object hypotheses |
| Segmentation | YOLOv8n-seg | instance masks |
| Relative depth | MiDaS small | monocular relative depth cue, not metres |
| Pose | YOLOv8n-pose | human keypoints and coarse activity |
| Optional VLM | LLaVA/VILA via Ollama-compatible API | on-demand narration |

## 3. Scheduler

The scheduler separates two concerns:

1. **Attention demand:** PATROL / ALERT / ENGAGED, driven primarily by fused
   scene risk.
2. **Resource condition:** NORMAL / CONSTRAINED / CRITICAL, driven by runtime
   telemetry.

Each state machine has hysteresis. Risk is considered before load shedding, so
resource pressure cannot silently turn a high-risk scene into a normal patrol
decision. Under CRITICAL resources, the scheduler chooses a degraded feasible
plan and uses frame skipping with explicit `skipped=true` telemetry.

A documented development failure mode was a starvation loop in which ENGAGED
lowered FPS, low FPS was interpreted as starvation, and starvation prevented
de-escalation. The current design has independent resource recovery hysteresis
and tests for sustained starvation, high risk under load, and safe recovery.

## 4. Fusion and confidence

Fusion associates class-consistent masks with detections, samples relative
depth, associates valid pose keypoints with people, and performs lightweight
class-aware tracking using IoU and centroid gating. Motion uses timestamps, not
pixels per frame.

Per-object risk uses transparent heuristics over class, relative proximity,
motion and pose state. `decision_confidence` is a **heuristic decision
confidence**, not a statistically calibrated uncertainty estimate.

## 5. ROS 2 interface

| Topic | Meaning |
|---|---|
| `/perception/objects` | `vision_msgs/Detection2DArray`; class and score only |
| `/perception/scene` | JSON scene description with `rel_depth`, activity, risk and backend provenance |
| `/perception/risk` | scalar fused scene risk |
| `/perception/semantic_image_grid` | 16x12 image-space semantic grid; not a metric occupancy map |
| `/perception/status` | mode, attention/resource state, model list, backend, FPS and validated latency |

Relative monocular depth is deliberately **not** written into ROS
`pose.position.z` because it is not metric.

## 6. Experiments

### Experiment 1 - model/format throughput

`benchmark/fps_test.py` measures canonical model latency/FPS for the selected
backend. `benchmark/format_test.py` compares execution formats, with explicit
notes about what is and is not directly comparable. TensorRT engines must be
built and measured on the target Jetson.

### Experiment 2 - adaptive vs fixed scheduler

Run:

```bash
python -m benchmark.latency_test --frames 120
```

The generated Markdown/JSON are the evidence. "Cost proxy units" are manually
assigned model-cost scores summed only over models that actually executed.
They are **not** measured joules, watts, CPU usage or TOPS.

### Experiment 3 - fused scene-understanding demo

Run:

```bash
python -m benchmark.understanding_demo --backend mock
# or, with real dependencies/weights available:
python -m benchmark.understanding_demo \
  --image assets/test_bus.jpg --backend real
```

The output uses `rel_depth` in the normalized convention `0=near, 1=far`.
No result is labelled in metres.

### Experiment 4 - ROS 2 latency

The ROS node reports camera-stamp-to-publish latency only when the clock
domains are compatible. Gazebo launches use simulation time. Invalid,
negative or implausible timestamps are reported as unavailable rather than as
a misleading latency.

## 8. Limitations and future work

- Replace relative depth with calibrated RGB-D, stereo, LiDAR fusion or a
  validated metric-depth model where metric range is required.
- Evaluate perception quality on labelled datasets using task-appropriate
  metrics rather than pseudo-label agreement.
- Evaluate power and thermal behaviour on target Jetson hardware.
- Replace heuristic confidence with calibrated uncertainty if downstream
  safety gating requires probabilistic confidence.
- Compare the state-machine scheduler with contextual-bandit or other learned
  scheduling policies.
- Upgrade tracking to a validated multi-object tracker for crowded scenes.
